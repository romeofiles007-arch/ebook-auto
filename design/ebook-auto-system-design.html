01ของที่มีอยู่แล้ว

ช่องว่างที่โปรเจกต์นี้ยึด

(1) ขับ ChatGPT ผ่าน UI เป็นร้อยเทิร์นแบบมีสถานะ กู้คืนได้ ไม่ใช่ยิงทีละคำถาม (2) ลูปที่วัดจำนวนหน้าจาก PDF จริงแล้ววนแก้จนตรงเป้า (3) เรียงพิมพ์และแก้ไขจบในเบราว์เซอร์ ไม่มีเซิร์ฟเวอร์ (4) งานเรียงพิมพ์ภาษาไทยที่ถูกต้อง ซึ่งไม่มีตัวไหนแตะเลย

ข้อควรรู้ก่อนตัดสินใจ

การใช้สคริปต์ขับหน้าเว็บ ChatGPT ขัดกับเงื่อนไขการใช้บริการของ OpenAI ที่กำหนดให้เข้าถึงแบบอัตโนมัติผ่าน API เท่านั้น ความเสี่ยงคือบัญชีถูกจำกัดหรือระงับ และการเปลี่ยนหน้าตาเว็บทำให้ระบบพังโดยไม่เตือนล่วงหน้า — นี่เป็นการตัดสินใจของคุณ ผมออกแบบให้ตามที่สั่ง แต่จะวาง ชั้น transport ที่สลับได้ ไว้ให้ (หัวข้อ 03) เพื่อให้ย้ายไปใช้ API หรือโมเดลโลคัลได้ในภายหลังโดยไม่ต้องรื้อระบบ และเพื่อให้ทดสอบส่วนอื่นได้โดยไม่ต้องยิง ChatGPT ทุกครั้ง

02สถาปัตยกรรมส่วนขยาย

ระบบมีสามกระบวนการที่คุยกันผ่านข้อความ ประเด็นสำคัญที่สุดของการออกแบบนี้คือ สมองอยู่ที่ไหน

การตัดสินใจที่สำคัญที่สุดของสถาปัตยกรรม

ห้ามวางตัวควบคุมงานไว้ใน service worker เพราะ Manifest V3 ฆ่า service worker เมื่อไม่มีงานประมาณ 30 วินาที การผลิตหนังสือหนึ่งเล่มใช้เวลาเป็นชั่วโมงและมีช่วงรอนาน ๆ ระหว่างเทิร์น ถ้าวางไว้ที่นั่น งานจะตายกลางทางแบบสุ่มและหาสาเหตุยากมาก ให้วางสมองไว้ที่ Studio tab ซึ่งเป็นหน้าเว็บของส่วนขยายที่เปิดค้างไว้ตลอดงาน — มันไม่ถูกฆ่า มี IndexedDB มี DOM รัน WASM ได้ และเป็น UI อยู่แล้ว ส่วน service worker ลดบทบาทเหลือแค่ตัวส่งต่อข้อความและตัวปลุกงานเมื่อแท็บถูกปิด

หน้าตาของส่วนขยาย: ใช้ทั้งสามพื้นผิว

Chrome ให้ที่วาง UI สามแบบ และคำตอบไม่ใช่การเลือกอันเดียว แต่คือ ใช้ทั้งสามแบบตามหน้าที่ เพราะงานนี้มีสองโหมดที่ต้องการพื้นที่ต่างกันมาก — โหมดเฝ้าดูตอนเครื่องเดิน กับโหมดแก้ไขตอนคนทำงาน

พื้นผิวอายุพื้นที่ใช้ทำอะไรในระบบนี้
Popup
กดที่ไอคอน		 ตายทันทีที่คลิกที่อื่น เล็กมาก เป็นแค่ปุ่มเปิด — สถานะย่อสามบรรทัด + ปุ่ม “เปิด Studio” และ “หยุด” ห้ามวางอะไรที่มีสถานะไว้ที่นี่เด็ดขาด
Side panel
แถบข้าง · แนะนำให้มี		 อยู่ได้ตราบที่ผู้ใช้ไม่ปิด · สลับแท็บไปมาไม่รีโหลด ไม่รีเซ็ตสถานะ แคบ ราว 320–500 px ลากขยายได้บ้าง จอเฝ้างาน — เปิดคู่ไปกับแท็บ ChatGPT เพื่อดูว่ากำลังเขียนตอนไหน เทิร์นที่เท่าไร เหลืออีกกี่ตอน หน้าที่ได้เทียบเป้า พร้อมปุ่มหยุด/ทำต่อ/ข้ามตอนนี้ — เป็นหน้าจอล้วน ไม่ถือสถานะเอง
Tab เต็ม
Studio · ปักหมุดไว้		 อยู่จนกว่าจะปิด เต็มจอ สมองและโต๊ะทำงาน — เครื่องสถานะ ฐานข้อมูล Typst WASM และหน้าจอแก้ไขสองบานคู่
ทำไมสมองต้องอยู่ในแท็บ ไม่ใช่ในแถบข้าง

แถบข้างน่าใช้กว่ามากในแง่การเฝ้างาน แต่มีสองอย่างที่ตัดสิทธิ์ไม่ให้เป็นสมอง: ผู้ใช้ปิดมันได้ด้วยคลิกเดียว ซึ่งจะทำให้งานที่เดินอยู่หยุดกลางคัน และ กว้างไม่พอสำหรับหน้าจอแก้ไข — โหมดแก้ไขคือต้นฉบับข้างหนึ่ง หน้ากระดาษจริงอีกข้างหนึ่ง ยัดลงพื้นที่ 400 px ไม่ได้ ให้เปิด Studio เป็นแท็บที่ ปักหมุด ไว้ (ปิดยากโดยไม่ตั้งใจ) แล้วให้แถบข้างเป็นแค่หน้าต่างมองเข้าไปในงานที่แท็บนั้นทำอยู่ ทั้งสองคุยกันผ่าน service worker เหมือนกับ content script

รายละเอียดที่ต้องรู้ตอนเขียน: side panel ต้องขอสิทธิ์ "sidePanel" และประกาศ "side_panel": { "default_path": "panel.html" } ใน manifest · ใช้ได้ตั้งแต่ Chrome 114 · เปิดด้วยโค้ดได้เฉพาะเมื่อผู้ใช้เพิ่งกดอะไรสักอย่าง ไม่ใช่เปิดเองตามใจ · ตั้ง setPanelBehavior({ openPanelOnActionClick: true }) แล้วกดไอคอนส่วนขยายจะเปิดแถบข้างแทน popup ซึ่งอาจเป็นทางเลือกที่ดีกว่ามี popup แยก

แท็บที่ปักหมุดก็ยังถูกทิ้งได้

Chrome ทิ้งแท็บพื้นหลังได้เมื่อหน่วยความจำตึง (Memory Saver) แท็บปักหมุดโดนน้อยกว่าแต่ไม่ปลอดภัยร้อยเปอร์เซ็นต์ ทางกันคือกลไกเดียวกับที่ออกแบบไว้แล้วในหัวข้อ 10 — เขียนผลทุกเทิร์นลง IndexedDB ก่อนไปต่อ แล้วให้ service worker ใช้ chrome.alarms ตรวจเป็นระยะว่าแท็บ Studio ยังอยู่ไหม ถ้าหายให้เปิดใหม่แล้วทำต่อจากเทิร์นล่าสุดโดยอัตโนมัติ ผู้ใช้แทบไม่รู้ว่าเกิดอะไรขึ้น

ทางเดินของข้อความหนึ่งเทิร์น

  1. studio → sw ขอเทิร์นถัดไป พร้อมข้อความที่ประกอบเสร็จแล้ว และรหัสตอนที่คาดหวัง
  2. sw → tab หาแท็บ chatgpt.com ที่เปิดอยู่ ถ้าไม่มีให้เปิดใหม่ในหน้าต่างแยก
  3. sw → content ส่งงานผ่านพอร์ตที่ค้างไว้
  4. content โฟกัสช่องพิมพ์ → ใส่ข้อความ → กดส่ง → ตั้ง MutationObserver
  5. content เมื่อปุ่มหยุดหายไปและ DOM นิ่งครบ 1.5 วินาที ถือว่าจบเทิร์น
  6. content → studio ส่งข้อความดิบกลับ พร้อมสถานะ (ปกติ / ถูกตัด / ชนลิมิต / ปฏิเสธ)
  7. studio แกะ sentinel ตรวจรหัสตอน นับอักษร เขียนลง IndexedDB ทันที
  8. studio ตัดสินใจ: ไปตอนถัดไป / สั่งเขียนต่อ / ลองใหม่ / หยุดรอคน

manifest.json — จุดที่พลาดบ่อย

{
  "manifest_version": 3,
  "name": "Ebook Auto",
  "permissions": ["storage", "unlimitedStorage", "downloads",
                   "tabs", "scripting", "alarms", "sidePanel"],
  "host_permissions": ["https://chatgpt.com/*", "https://chat.openai.com/*"],
  "background": { "service_worker": "sw.js", "type": "module" },
  "side_panel": { "default_path": "panel.html" },   // จอเฝ้างาน
  "action": { "default_title": "Ebook Auto" },        // ไม่ตั้ง popup
  "content_scripts": [{
    "matches": ["https://chatgpt.com/*"],
    "js": ["adapter/chatgpt.js"],
    "run_at": "document_idle"
  }],
  // ⬇ ไม่มีบรรทัดนี้ Typst WASM จะโหลดไม่ขึ้น และ error จะไม่บอกสาเหตุ
  "content_security_policy": {
    "extension_pages": "script-src 'self' 'wasm-unsafe-eval'; object-src 'self'"
  },
  "web_accessible_resources": [{
    "resources": ["wasm/*", "fonts/*"],
    "matches": ["https://chatgpt.com/*"]
  }]
}

const RE = /<<<SEC ([\d.]+) BEGIN>>>([\s\S]*?)<<<SEC \1 END>>>/;

export function extract(rawText, expectId) {
  const m = rawText.match(RE);
  if (!m)                    return { status: "truncated" };  // ไม่เจอ END
  if (m[1] !== expectId)     return { status: "wrong_section" };
  const body = m[2].trim();
  if (body.length < 200)     return { status: "refused" };      // สั้นผิดปกติ
  return { status: "ok", body, chars: countThaiGraphemes(body) };

จ. บริบท: อย่าพึ่งความจำของเธรด

สัญชาตญาณแรกคือคุยในเธรดเดียวยาว ๆ แล้วให้ ChatGPT จำเอง อย่าทำ เพราะสามเหตุผล: เธรดยาวทำให้ตอบช้าลงเรื่อย ๆ จนช้ามากตอนบทท้าย ๆ · โมเดลจะเริ่ม drift และวนพูดซ้ำของเดิม · และถ้าเธรดเสียหายก็เสียทั้งเล่ม

กฎการจัดการเธรด

  • หนึ่งเธรดต่อหนึ่งบท ประมาณ 4–6 เทิร์น ยาวกำลังดี
  • เปิดเธรดใหม่ด้วย primer หนึ่งข้อความ: thesis ของเล่ม + voice card + สรุปเรื่องที่ผ่านมา + ศัพท์ที่ตกลงแล้ว
  • เทิร์นถัดไปในเธรดเดียวกันส่งแค่โครงตอน + โควตา เพราะบริบทอยู่ในเธรดแล้ว
  • ความจริงทั้งหมดอยู่ใน IndexedDB ฝั่งเรา เธรดเป็นแค่ที่ทำงานชั่วคราวที่ทิ้งได้

จังหวะการยิง

  • หน่วงสุ่ม 4–9 วินาทีระหว่างเทิร์น ไม่ใช่ค่าคงที่
  • หน่วงยาวขึ้น 20–40 วินาทีเมื่อขึ้นเธรดใหม่
  • เพดานต่อชั่วโมงที่ตั้งเองได้ และหยุดเมื่อถึง
  • ปุ่มหยุดที่หยุดได้จริงภายในเทิร์นปัจจุบัน ไม่ใช่รอจนจบเล่ม
  • บันทึกทุกเทิร์นลงดิสก์ก่อนยิงเทิร์นถัดไป เสมอ

ค. ลูปป้อนกลับหลังเรียงพิมพ์

for (let round = 1; round <= 3; round++) {
  const pdf   = await typst.compile(assemble(book));
  const pages = pdf.pageCount;              // จากไฟล์จริง
  const err   = pages - book.targetPages;

  if (Math.abs(err) <= book.tolerance) break;

  if (Math.abs(err) / book.targetPages <= 0.02) {
    nudgeLayout(err);        // ไม่แตะเนื้อหา: leading ±2%, ระยะย่อหน้า, widow/orphan
  } else {
    for (const s of pickElastic(err)) {
      await rewriteSection(s, errShare(s) * charsPerPage);  // ← ยิง ChatGPT
    }
  }
}

1. อย่ากระจายส่วนต่างให้ทุกตอนเท่า ๆ กัน — เวอร์ชันแรกทำแบบนั้นแล้วลูปไม่ลู่เข้าเลย วนอยู่ที่ 205–208 หน้าจากเป้า 200 ด้วยเหตุผลสองข้อ: ส่วนแบ่งของแต่ละตอนเล็กจนต่ำกว่าเกณฑ์ขั้นต่ำแล้วถูกตัดทิ้ง ส่วนต่างจึงถูกแก้ไม่ครบ และโมเดลคุมความยาวได้แค่ราว ±15% ทุกตอนที่แตะจึงเติมเสียงรบกวนเข้ามา ยิ่งแตะหลายตอนเสียงยิ่งกลบสัญญาณ ต้องทำตรงข้าม: รวมส่วนต่างไว้กับตอนที่มีที่ว่างมากที่สุด แตะให้น้อยตอนที่สุด และใช้ส่วนต่างให้ครบจำนวน ไม่ปัดทิ้ง

2. การคอมไพล์เล่มจริงครั้งแรกคือข้อมูล calibration ที่ดีที่สุดที่มี — ตัวอย่างที่ใช้ตอน calibrate เป็นข้อความล้วน ไม่มีหัวบท ไม่มีย่อหน้าสั้น พอเจอเล่มจริงค่าจึงคลาด ถ้าพลาดเกิน 3% ให้คำนวณอักษรต่อหน้าใหม่จากเล่มที่เพิ่งวัด แล้ว ตั้งโควตาใหม่ทุกตอนจากฐานที่ถูก ซึ่งย้ายกรอบ ±25% ไปด้วย ทำให้มีที่ว่างให้แก้อีกครั้ง ทดสอบแล้วแม้ตั้งค่าเริ่มต้นผิดไป +33% หรือ −25% ลูปก็ลู่เข้าใน 3 รอบ

กติกาที่ทำให้ลูปนี้ไม่พังคุณภาพ

ห้ามสั่ง “เขียนให้ยาวขึ้น” ลอย ๆ เพราะโมเดลจะเติมน้ำ คำสั่งยืดต้องระบุวิธี — เพิ่มตัวอย่างสถานการณ์จริงหนึ่งเคส เพิ่มตัวเลข/ข้อมูลอ้างอิง เพิ่มขั้นตอนปฏิบัติ ส่วนคำสั่งหดต้องระบุ — รวมย่อหน้าที่พูดเรื่องเดียวกัน ตัดคำขยายซ้ำ ย้ายรายละเอียดปลีกย่อยไปอภิธานศัพท์ และทุกครั้งต้องส่ง takeaways กลับเข้าไปเป็นข้อห้ามตัดทิ้ง พร้อมกรอบ ±25% ต่อตอนที่ลูปห้ามข้าม

09งานภาษาไทย

ความเสี่ยงข้อแรกที่ต้องทดสอบก่อนเขียนโค้ดอย่างอื่น

ภาษาไทยไม่มีช่องว่างระหว่างคำ เครื่องมือเรียงพิมพ์จึงต้องมีพจนานุกรมถึงจะรู้ว่าตัดบรรทัดตรงไหนได้ ถ้าไม่รู้ ผลคือบรรทัดยืดผิดปกติหรือตัดกลางคำจนอ่านสะดุด วันแรกของโปรเจกต์ ให้เขียนหน้าเดียวที่โหลด typst.ts แล้วเรียงพิมพ์ย่อหน้าไทยจริง 20 บรรทัด แล้วดูด้วยตา อย่าเชื่อเอกสาร รวมถึงหน้านี้

ทางแก้ที่ควบคุมได้เอง

ไม่ว่าเครื่องมือจะรองรับหรือไม่ ให้ตัดคำเองในขั้น pre-process แล้วแทรก zero-width space (U+200B) ระหว่างคำ วิธีนี้ทำให้เครื่องมือตัดบรรทัดถูกจุดโดยไม่ต้องรู้ภาษาไทย และเราคุมคุณภาพเองได้ ข้อดีเพิ่มเติมในบริบทส่วนขยายคือ ทำได้ใน JavaScript ล้วน ไม่ต้องมี Python

// ตัวเลือกฝั่ง JS ที่ใช้ได้ในส่วนขยาย:
//  1) Intl.Segmenter — มีในเบราว์เซอร์อยู่แล้ว ไม่ต้องแนบอะไรเพิ่ม
//  2) พจนานุกรมไทย + longest-matching เขียนเอง ~100 บรรทัด แม่นกว่า

const seg = new Intl.Segmenter("th", { granularity: "word" });

function prepareThai(md) {
  // ข้ามบล็อกโค้ด ลิงก์ และตัวเลข ไม่ให้แตกกลางคัน
  return mapProseOnly(md, (text) =>
    [...seg.segment(text)].map(s => s.segment).join("​"));
}

ผลข้างเคียงที่ต้องจัดการ: ZWSP จะติดไปกับข้อความเวลาผู้อ่านคัดลอกจาก PDF ให้ลบออกในเวอร์ชัน EPUB และในต้นฉบับที่เก็บไว้ — เก็บ ZWSP ไว้เฉพาะในสายที่ป้อนเข้าคอมไพเลอร์เท่านั้น และ อย่าลืมว่าโควตาอักษรต้องนับก่อนแทรก ZWSP ไม่งั้นตัวเลขจะเพี้ยนทั้งระบบ

รายละเอียดอื่นที่ทำให้เล่มดูเป็นมืออาชีพ

  • ขนาดตัวอักษร — ฟอนต์ไทยมีความสูงตัวพิมพ์เล็กกว่าละตินที่ point เดียวกัน ตั้ง 14–16pt สำหรับเนื้อความ ไม่ใช่ 11pt แบบหนังสืออังกฤษ
  • ระยะบรรทัด — ต้องเผื่อวรรณยุกต์และสระบน–ล่างสองชั้น ใช้ 1.6–1.8 เท่า ไม่ใช่ 1.4
  • เลือกฟอนต์ให้ถูกงาน — แบบมีหัว (Sarabun, TH Sarabun, IBM Plex Sans Thai) อ่านสบายกว่าสำหรับเนื้อความยาว แบบไม่มีหัวเก็บไว้ใช้กับหัวเรื่อง และต้องเป็นฟอนต์ที่ใบอนุญาตให้ฝังในไฟล์เพื่อการค้าได้
  • การจัดชิดขอบสองข้าง — ไทยไม่มียัติภังค์ การ justify จึงต้องยืดช่องว่างระหว่างคำ ให้กำหนดเพดานการยืดไว้ ไม่งั้นจะเกิด “แม่น้ำ” ช่องว่างพาดกลางหน้า ถ้าคุมไม่ได้ ใช้ชิดซ้ายแทน ดูดีกว่า justify ที่แย่
  • การนับอักษร — สระและวรรณยุกต์เป็น combining character อย่านับด้วย str.length ให้ normalize เป็น NFC แล้วนับด้วย Intl.Segmenter granularity grapheme

(1) ให้ ChatGPT สร้างภาพปกหน้าและปกหลังแยกกัน โดยใช้ style token ชุดเดียวกัน (2) ดึงภาพกลับ: content script อ่าน src ของภาพในคำตอบ แล้ว fetch เป็น Blob เก็บลง IndexedDB (3) ดูดสีเด่นจากขอบภาพมาไล่เฉดเป็นพื้นสัน (4) ประกอบทั้งสามส่วนใน Typst และ เรียงพิมพ์ตัวหนังสือทุกตัวด้วย Typst ทับลงไป ทั้งชื่อเรื่อง ชื่อผู้แต่ง คำโปรย ISBN — ตัวหนังสือบนปกต้องคมและสะกดถูก ซึ่งมีทางเดียวคือเรียงพิมพ์เอง ห้ามให้โมเดลภาพวาดตัวอักษร

คำตอบหนึ่งเทิร์นยาวได้จำกัดตอนหนึ่งไม่ควรเกิน ~6,000–8,000 อักษร ซึ่ง บังคับรูปร่างของหนังสือ ให้เป็นตอนสั้นจำนวนมาก ไม่ใช่บทยาว ๆ ไม่กี่บทบังคับตั้งแต่ขั้นสารบัญ ถ้าโควตาตอนไหนเกินให้แตกเป็นสองตอน อย่าไปแก้ทีหลังด้วยการสั่งเขียนต่อ
ต้องเปิดเครื่องและเปิดแท็บค้างไว้ไม่ใช่บริการบนคลาวด์ ปิดโน้ตบุ๊ก = งานหยุด (กลับมาทำต่อได้ แต่ไม่เดินเอง)เหมาะกับการสั่งงานตอนกลางคืนบนเครื่องที่ไม่ได้ปิด ไม่เหมาะกับการสั่งจากมือถือ
คุณภาพเนื้อหา = คุณภาพของโมเดลระบบทำให้ ยาวตามสั่ง ไม่ซ้ำ และต่อกันลื่น ได้ แต่ทำให้ ลึกขึ้น ไม่ได้ ถ้าโมเดลไม่รู้จริงในหัวข้อนั้น หนังสือก็จะตื้นทั้งเล่มอย่างสม่ำเสมอป้อนวัตถุดิบของคุณเองเข้าไปใน primer — ข้อมูล ประสบการณ์ ตัวเลขจริง นี่คือสิ่งที่ทำให้หนังสือต่างจากที่คนอื่นกดออกมาได้
ไม่มีการตรวจข้อเท็จจริงจากภายนอกตัวเลข ชื่อคน กฎหมาย วันที่ อาจถูกแต่งขึ้นและอ่านดูน่าเชื่อถือมากบังคับกำกับที่มาทุกตัวเลข และต้องมีคนอ่านตรวจก่อนขายจริง โดยเฉพาะสายการเงิน สุขภาพ กฎหมาย
ความละเอียดภาพไม่พอสำหรับปกภาพจากหน้าเว็บได้ราว 170 dpi บนปก 6×9 นิ้ว ต่ำกว่าเกณฑ์งานพิมพ์ออกแบบปกให้ภาพเป็นแค่ส่วนหนึ่ง ที่เหลือให้ Typst วาดเป็นเวกเตอร์ (หัวข้อ 13)

เงื่อนไขการใช้บริการขัดกับ ToS ของ OpenAI มีความเสี่ยงต่อบัญชีชั้น transport ที่สลับไป API หรือโมเดลโลคัลได้ทันทีเมื่อจำเป็น

ข. แก้ได้ด้วยการออกแบบ — และเอกสารนี้แก้ให้แล้ว

ข้อเหล่านี้เป็นสิ่งที่ทำให้โปรเจกต์คล้าย ๆ กันใช้งานจริงไม่ได้ ทั้งที่ดูเหมือนทำงานได้ในเดโม

  • จำนวนหน้าไม่ตรง → ลูปวัดจาก PDF จริงแล้ววนแก้ (หัวข้อ 06)
  • เนื้อหาซ้ำข้ามบท → Book Bible ที่เราถือเอง ไม่พึ่งความจำของเธรด (หัวข้อ 07)
  • งานตายกลางทาง → สมองอยู่ในแท็บ ไม่ใช่ service worker + ทุกเทิร์นเขียนลงดิสก์ก่อนไปต่อ (หัวข้อ 02, 10)
  • ดึงข้อความกลับมาแล้วเพี้ยน → บังคับตอบในบล็อกโค้ดเดียว + sentinel (หัวข้อ 03)
  • ภาษาไทยตัดบรรทัดผิด → แทรก ZWSP ก่อนป้อนเข้าคอมไพเลอร์ (หัวข้อ 09)
  • ลูปยืด/หดทำให้เนื้อหาเป็นน้ำ → บังคับวิธียืดที่เพิ่มสาระ + กรอบ ±25% ต่อตอน (หัวข้อ 06)
ข้อเดียวที่ยังแก้ไม่หมด

ลูปนับหน้าไม่ลู่เข้าเสมอ ถ้าเป้าหมายหน้าไม่สมเหตุสมผลกับโครงเรื่อง เช่นสั่ง 500 หน้าจากสารบัญ 5 บท ระบบจะต้องยืดทุกตอนจนเกินเพดาน +25% แล้ววนไม่จบ ทางแก้คือ ตรวจตั้งแต่ขั้นอนุมัติสารบัญ ว่างบอักษรต่อตอนอยู่ในช่วงที่เขียนได้จริง (ราว 2,000–8,000 อักษร) ถ้าไม่อยู่ ให้เสนอปรับจำนวนบท/ตอน หรือปรับจำนวนหน้าเป้าหมาย ตั้งแต่ตอนนั้นเลย ดีกว่าปล่อยให้ไปพังตอนวนรอบที่สาม

ค. สิ่งที่ระบบนี้ตั้งใจไม่ทำ

ไม่ใช่

  • ผู้ช่วยเขียนแบบนั่งเขียนไปด้วยกัน — ระบบนี้เดินเองจนจบแล้วให้คนมาแก้ทีหลัง
  • เครื่องมือเขียนนิยาย — โครงสร้าง บท/ตอน/จังหวะ/takeaways ออกแบบมาเพื่อ non-fiction
  • ระบบจัดจำหน่าย — จบที่ไฟล์ ไม่ยุ่งกับการอัปโหลดขึ้นร้าน
  • ระบบหลายคนใช้ร่วมกัน — ทุกอย่างอยู่ในเบราว์เซอร์เครื่องเดียว

ผลที่ตามมาที่ต้องรับมือ

  • งานทั้งหมดอยู่ใน IndexedDB ของเบราว์เซอร์ — ถ้าล้างข้อมูลเบราว์เซอร์ งานหาย
  • จึงต้อง ส่งออก project.json อัตโนมัติทุกครั้งที่จบบท ไม่ใช่รอให้ผู้ใช้กดเอง
  • ย้ายเครื่องได้ด้วยไฟล์เดียวกันนี้

ลำดับที่ควรสร้าง — เรียงตามความเสี่ยง ไม่ใช่ตามลำดับการทำงาน

  1. พิสูจน์สองอย่างในวันแรก ก่อนเขียนอะไรอย่างอื่น — (ก) หน้าเดียวที่โหลด typst.ts แล้วเรียงพิมพ์ย่อหน้าไทยจริง 20 บรรทัด ดูการตัดบรรทัดด้วยตา (ข) ส่วนขยายเปล่าที่ฉีดข้อความ “ตอบว่า OK” เข้า ChatGPT แล้วดึงคำตอบกลับได้ ถ้าสองอย่างนี้ไม่ผ่าน สถาปัตยกรรมทั้งหมดต้องเปลี่ยน — และรู้ตอนนี้ถูกกว่ารู้ตอนเดือนหน้ามาก
  2. ทำลูปนับหน้าให้ครบด้วย transport/fake.js — ตัวสร้างข้อความปลอมที่ยืด/หดได้ตามสั่ง ยังไม่ต้องยิง ChatGPT เลย พิสูจน์ว่าลูปทำให้หน้าตรงเป้าได้จริง นี่คือหัวใจของระบบและเป็นส่วนที่ต้องแน่ก่อน
  3. ต่อ transport ตัวจริง พร้อม healthcheck, sentinel, การจัดการเธรด และตารางความพังในหัวข้อ 10 — ทำเรื่องความพังตั้งแต่ตอนนี้ อย่าเลื่อนไปทีหลัง
  4. ขั้นสารบัญ + ประตูอนุมัติ พร้อม schema validation
  5. ขั้นเขียนเนื้อหา + Book Bible แล้วปล่อยให้เดินครบเล่มหนึ่งรอบ
  6. โหมดแก้ไข — สองบานคู่ + พรีวิว SVG + ปุ่มเขียนใหม่ + สถานะจำนวนหน้า
  7. ปก + preflight เป็นขั้นสุดท้าย เพราะต้องใช้จำนวนหน้าสุดท้าย
