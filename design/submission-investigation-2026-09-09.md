# ตรวจทางส่งข้อความ 9 กันยายน 2026

## หลักฐานจากโค้ด

- sendCandidates เคยค้นทั้ง form และ document รวมถึงปุ่ม submit ที่ไม่ใช่ช่อง ChatGPT
- clickSend เคยวนคลิกหลายปุ่มและส่ง synthetic Enter หลายครั้ง แล้ว runTurn เรียก clickSend ซ้ำอีกรอบก่อนถึง native fallback
- accepted() เคยรับช่องว่างหรือปุ่ม Stop ที่เพิ่งปรากฏเป็นหลักฐาน ขณะที่ runTurn ใช้อีกเกณฑ์หนึ่งคือจำนวนข้อความผู้ใช้ต้องเพิ่ม ทำให้สองชั้นไม่เห็นตรงกัน
- การนับจำนวนข้อความไม่พอเมื่อหน้าเปลี่ยนชุด DOM; จำลองกรณีจำนวนเท่าเดิมแต่ข้อความใหม่มี ID ใหม่ได้
- gpt.run ไม่มีตัวกันเทิร์นซ้อน และ worker ไม่ตรวจผลตอบรับจาก adapter

นี่เป็นข้อบกพร่อง/ช่องโหว่ของเส้นทางในโค้ด ไม่ใช่หลักฐานว่าทุกครั้งที่ผู้ใช้พบเกิดจากสาเหตุเดียวกัน ไม่มีการอ้างว่า ChatGPT ปฏิเสธ event.isTrusted=false โดยตรง

## การแก้

ค้นปุ่มเฉพาะ form ของช่องพิมพ์ คลิก DOM หนึ่งครั้ง รอข้อความที่ตรงกับ Prompt และเป็นข้อความใหม่ ตรวจ ID ร่วมกับจำนวนรายการข้อความที่ตรงกัน ไม่ถือช่องว่างเป็นหลักฐานว่าส่งสำเร็จ

ถ้ายังมี draft เดิมและไม่มีงานกำลังตอบ ใช้ native fallback หนึ่งครั้ง โดยตรวจ draft และสถานะ busy ซ้ำก่อนแตะ input ถ้าช่องเปลี่ยนหรือผลไม่ชัดเจน ให้รอ receipt และรายงาน outcome_unknown แทนการส่งข้อความซ้ำโดยเดา

Adapter รับได้ครั้งละหนึ่งเทิร์น คำขอ ID เดิมระหว่างทำไม่ส่งซ้ำ หลังจบ replay ผลเดิมได้จาก cache 10 รายการ Worker รับรู้การปฏิเสธงานซ้อนจริง

เพิ่มเหตุการณ์ submitted และ meta.sendMs / meta.answerMs เพื่อแยกเวลาจนส่งสำเร็จออกจากเวลารอคำตอบ ตัวเลขเวลาทดสอบไม่ใช่ความเร็วสร้างหนังสือจริง

## ตรวจสอบและข้อจำกัด

ทดสอบ receipt ตรง Prompt, old message rerender, DOM count เท่าเดิมแต่ ID ใหม่, จำกัด form, ไม่วนคลิก/Enter, serialize/replay, draft เปลี่ยน และ busy ก่อน fallback พร้อมชุดเดิมเรื่องแนบภาพ/กู้ภาพและ flow

ไม่ได้รีโหลดหรือควบคุมแท็บงานจริง และยังไม่ได้ยืนยัน end-to-end ผ่าน ChatGPT จริง การทดสอบใช้โค้ดจริงกับ DOM/Chrome API จำลอง ไม่ใช้โควตา ChatGPT

เอกสารอ้างอิงเรื่อง scripted events ต่างจาก user-agent events: https://developer.mozilla.org/en-US/docs/Web/API/Event/isTrusted
